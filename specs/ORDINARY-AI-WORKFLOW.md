# 普通對話 AI 整理規格流程

普通對話 AI 只負責整理草稿，不負責產品決策，也不直接把文件升級成正式規格。

## 最簡單的使用方式

執行 `npm run knowledge:review-packets` 後，到 `output/pdf/ai-spec-review-packets/` 選擇一份功能 PDF。每份 PDF 已包含規格、圖片、來源、第一輪整理提示詞及第二輪缺漏檢查提示詞，不需要另外下載圖片。

## 準備材料

一次只處理一個功能，提供：

- `AI-SPEC-WORK-QUEUE.md` 中該功能的正式規格連結。
- 對應畫面截圖與 Figma 連結。
- 新取得的產品決定、User Story、API、欄位或 QA 規則。
- 若 AI 無法瀏覽 GitHub，直接貼上 Markdown 內容並附圖。

沒有新增證據時，AI 只能整理現有文字，不能自行回答待確認事項。

## 可直接複製的提示詞

```text
你是後台產品規格整理助手。請把我提供的資料整理成簡短、白話、可讓規劃、前端、後端與 QA 閱讀的規格草稿。

功能名稱：
[填入]

正式規格或現有草稿：
[貼上 GitHub 連結或 Markdown]

畫面與 Figma：
[附圖並貼上連結]

本次新增的已確認資料：
[貼上產品決定、User Story、API、欄位或 QA 規則；沒有就寫「無」]

請遵守：
1. 只能使用我提供的文字、圖片與連結。
2. 畫面直接看得到的內容可以寫成「畫面目前顯示」。
3. 只有我明確提供的新決定才能寫成「已確認」。
4. 權限、API、驗證、限制、錯誤處理、保存、成功結果與例外流程，沒有資料就保留「待確認」。
5. 不可依一般產品經驗自行補答案。
6. 使用簡單繁體中文，不解釋 AI、索引、Claim、JSON 或元件 Key。
7. 保留原有圖片與 Figma 來源，不可編造新連結。
8. 如果資料互相矛盾，列在「待確認」。

請輸出：
# 功能名稱
- 文件狀態：草稿，待人工檢閱
- 所屬模組
- 最後更新

## 功能說明
## 畫面與簡單說明
## 操作流程
## 各單位可以先使用的資訊
## 已確認規則
## 待確認
## Review

最後另外列出：
- 本次使用的來源
- 新增或修改了哪些內容
- 哪些問題仍然無法回答
```

## 人工 Review

只檢查：

1. 功能名稱與用途是否正確。
2. 圖片與功能分組是否正確。
3. 新增的已確認內容是否真的有來源。
4. AI 是否把待確認內容寫成確定事實。

通過後交給 Codex：

```text
這份草稿已人工確認。請更新對應正式 specs、保留圖片與來源、同步 query-index、執行所有驗證並建立 PR。不要自行增加產品規則。
```

若要先做第二輪缺漏檢查，將同一份 PDF 與第一輪草稿交給另一個 AI，使用 PDF 內的「第二輪」提示詞。最後只收回簡單問題與人工答案，再交給 Codex 補回規格。
