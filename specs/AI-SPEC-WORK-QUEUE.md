## 怎麼使用

1. 一次只選一份規格，不要要求 AI 一次補完整個後台。
2. 將該規格的 GitHub 連結交給能瀏覽網頁的 AI；不能瀏覽時，貼上 Markdown 並附上畫面圖片。
3. 如果有新的產品決定、User Story、API 或 QA 規則，一起提供；沒有資料時，AI 必須保留「待確認」。
4. 使用 [`普通對話 AI 整理流程`](ORDINARY-AI-WORKFLOW.md) 中的提示詞產生草稿。
5. 人工只檢查名稱、用途、圖片分組與是否出現推測。
6. 通過後交給 Codex 更新正式文件、索引、驗證並建立 PR。

## 建議處理順序

- **P1 核心流程**：先補新增、編輯、單一更新與批次更新。這些缺口會直接影響前端、後端與 QA。
- **P2 圖片檢視**：再補縮放、圖片方向、載入失敗與操作權限等規則。
- 普通 AI 可以整理新證據與改寫文件，但不能自行決定下列待確認答案。

### 新增事件主類別

- 正式規格：[GitHub 開啟](https://github.com/IsumiOuO/backoffice-design-hub-knowledge/blob/main/specs/create-event-main-category.md)

待確認：

- 哪些角色可以新增事件主類別。
- 是否有其他權限條件。
- 主類別名稱是否必填。
- 名稱的字數限制。
- 可輸入的內容或格式限制。
- 各語系是否都有必填要求。
- 不同語系資料之間的保存與送出規則。
- 是否可以完全不選事件次類別。
- 最多可以選擇幾個事件次類別。
- 是否有其他選擇限制。
- 是否可以完全不選發布介面。
- 圖片是否必填。
- 支援哪些圖片格式。
- 圖片尺寸限制。
- 圖片容量限制。
- 圖片數量限制。
- 返回前一步後，原本已輸入或已選擇的資料是否保留。
- 關閉視窗時，已輸入資料如何處理。
- 按下「取消」時，已輸入資料如何處理。
- 使用「清空內容並重新填寫」時，是否需要再次確認。
- 關閉、取消或清空後，資料是否會被保存。
- 各欄位實際驗證條件。
- 各步驟錯誤畫面的觸發條件。
- 驗證失敗時的錯誤訊息。
- API 失敗或其他系統錯誤如何處理。
- Step 4 按下「新增」後實際會建立哪些資料。
- 新增成功的判定方式。
- 新增成功後何時生效。
- 新增成功後導向哪個畫面。
- 新增失敗時如何處理。
